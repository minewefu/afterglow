### Residuals on partial fixes

**D-03.** `StressAdapter.SelectNvidia` picks *the NVIDIA adapter with the largest dedicated
VRAM*. It takes no GPU-identity parameter, so on a system with two NVIDIA cards the burn is
still not bound to the tuned one (`Gpus[0]` is the first NVML device, not necessarily the
largest-VRAM adapter). The dangerous and common case — an iGPU winning DXGI order — is closed,
and the engine now fails loudly when no NVIDIA adapter exists. *To close fully: pass the tuned
GPU's PCI bus/device/function or LUID into `SelectNvidia` and match on it.*

**D-04.** `AppliedStateStore` records are now stamped with the GPU UUID, and `GpuTuner` adopts a
persisted lock only when the UUID matches (or is absent, for legacy files). That closes the
harmful case: no card can inherit another card's clock lock. Still outstanding: it remains a
single file, so on a multi-GPU system the last `Apply` overwrites the other card's record, and
`RecordFans` / `RecordPending` do not stamp a UUID. The README now discloses the single-GPU GUI
under *Honest limitations*, which was the other half of this finding.

**D-16.** The floor is now a named constant with a comment stating plainly that it is not
driver-derived, and `InvalidArgument` produces an explanatory message naming the floor. NVML
exposes no queryable minimum locked clock, so this is close to the ceiling of what the public
API allows. Recorded as mitigated rather than fixed because the underlying assumption is
unchanged.

### D-19 was fixed better than proposed

Round 1 suggested keying the NVML/NVAPI pairing on `domain:bus:device.function`. NVAPI's
`GetBusId` exposes only the bus number, so that key is not actually available. The
implementation instead *detects* the ambiguity and pairs **neither** GPU on a contested bus,
with a log line. That is the correct fail-safe and does not depend on an API that may not exist.

## Round 2: new findings

### N-01 — The D-14 fix introduced a fan-command race

`src/Afterglow.Core/Fans/FanControlService.cs:115-155`
**Severity: Low-Medium. Introduced by a round-1 fix.**

Moving driver calls outside `_lock` was the right change, but nothing now serialises the calls
themselves. `OnSnapshot` (telemetry poller thread) computes its duty under the lock, releases,
then commands; `SetFixed` / `SetAuto` (UI thread) do the same. The two can interleave:

```text
T0  poller   OnSnapshot: mode==Curve, duty=45, releases lock
T1  UI       SetFixed(80): lock -> mode=Fixed -> unlock -> driver set 80
T2  poller   Command(45) -> driver set 45          <-- stale command lands last
```

Fans end at 45% while the UI and applied-state say Fixed 80%. It does not self-correct: the next
`OnSnapshot` sees `_mode != Curve` and returns before commanding. The window is one driver call
(milliseconds), so a mode change has to land inside it — but the wrong state then persists until
the user touches the setting again.

`SetAuto` has the same shape: `RestoreAutoFansRaw()` can be followed by a stale curve command
that re-takes manual control.

**Fix:** add a separate command mutex that serialises `Command` / `RestoreAutoFansRaw`, or carry
a generation counter incremented under `_lock` and have `Command` drop its write when the
generation moved while it was outside.

### N-02 — MCP `isError` inspection throws on any non-object payload

`src/Afterglow.Cli/McpCommand.cs:145-161`
**Severity: Low. Latent — not reachable with today's ten tools.**

```csharp
var body = JsonNode.Parse(payload);
isError = body?["error"] is not null || ... ;
}
catch (JsonException) { }
```

String-indexing a `JsonNode` that is not a `JsonObject` throws `InvalidOperationException`, which
the filter does not catch. Confirmed experimentally:

```text
{"all_succeeded":false}  -> isError=True
[1,2,3]                  -> THROWS InvalidOperationException
"text"                   -> THROWS InvalidOperationException
42                       -> THROWS InvalidOperationException
```

All ten current tools return JSON objects, so nothing throws today. The hazard is that this sits
in the server's request loop: the first tool added that returns a bare array or scalar takes the
whole MCP server down.

**Fix:** test `if (body is JsonObject obj)` before indexing, or widen the filter to
`catch (Exception ex) when (ex is JsonException or InvalidOperationException)`.

### N-03 — `find_stable_offset` blocks unboundedly, unlike its siblings

`src/Afterglow.Cli/McpCommand.cs:456`
**Severity: Low.**

```csharp
stepper.Start(options);
done.Wait();          // no timeout
```

`run_stress` and `run_vram_test` both bound their waits (`done.Wait(TimeSpan)` inside a loop with
a hard `elapsed >= seconds * 3` escape). This one does not.

Every exit path in `StabilityStepper.Run` was traced — success, failure, no-headroom, unelevated
and cancelled all publish a terminal `Running=false` status, and the trailing `else` catches
`StressState.Failed` — so this is **not** a reachable hang today. The practical problem is
different: with the default `seconds_per_step = 60` and `max_offset_mhz = 300` the call can run
well over ten minutes with no cancellation path, and typical MCP clients time out far sooner. The
tool description does say it blocks, which is honest, but a client timeout leaves the stepper
running against the GPU with nobody reading the result.

**Fix:** accept a `max_minutes` argument, bound the wait, and call `stepper.Cancel()` on expiry so
the GPU is returned to the starting offset.

### N-04 — "verified at 100+ GiB/s" does not reproduce

`README.md:106`
**Severity: Claim accuracy.**

Measured on this hardware, driver 616.56:

```text
afterglow-cli vram --seconds 20  ->  29.0 GiB x  30 rounds  =  43.5 GiB/s
afterglow-cli vram --seconds 60  ->  29.0 GiB x 146 rounds  =  70.6 GiB/s
```

Both figures are self-consistent, and the rise with run length is the one-time allocation plus
first fill being amortised. Solving `total = T_setup + N * t_round` on the two points:

```text
t_round  = (60 - 20) / (146 - 30) = 0.3448 s per 29 GiB round
T_setup  = 20 - 30 * 0.3448       = 9.66 s
steady   = 29 / 0.3448            = 84.1 GiB/s     [extrapolated, not measured]
```

So even an arbitrarily long run trends toward roughly **84 GiB/s**, not 100+. The 84 figure is an
extrapolation from two points and is labelled as such; 43.5 and 70.6 are measured.

Caveats that could account for part of the gap, none of which were controlled for: the GPU was
warm (58 C and above) from immediately preceding burn tests, roughly 4.5 GiB of VRAM was in use
by other applications, and the original figure was recorded on driver 610.88 rather than 616.56.

**Fix:** re-measure on an idle machine and state the run length the number was taken at, or soften
it to a measured range. The tool prints its own live GiB/s, so this claim is easy for any user to
check — which is exactly why it should hold.

## Round 2 resolution (same day)

All four addressed; build clean, 94 tests pass.

- **N-01 — fixed.** `FanControlService` now serialises all driver fan calls behind a dedicated
  `_commandLock` *and* stamps every command with a generation captured at decision time
  (incremented under `_lock` on every mode change and on dispose). A command whose generation is
  stale by the time it holds the command lock is dropped **before** the driver call — the state
  update alone being dropped would still have let the stale duty land last. `SetAuto`'s restore
  carries the same check, closing the mirror-image race the finding described. Telemetry/UI
  threads still never block on a driver call in `_lock` (the D-14 property is preserved;
  `CommandFailed` is raised outside both locks).
- **N-02 — fixed.** The `isError` body inspection now pattern-matches `is JsonObject` before
  indexing and the catch is widened to `InvalidOperationException` as a second belt — a future
  tool returning an array or scalar can no longer take down the request loop.
- **N-03 — fixed.** `find_stable_offset` accepts `max_minutes` (5–120, default 30). On expiry it
  calls `stepper.Cancel()` — whose path was verified to restore the starting offset — waits up
  to 90 s for the restore to be confirmed, and returns `all_succeeded=false` with an honest note
  either way ("restored" vs "cancellation requested but not yet confirmed — verify the applied
  offset"). The timeout result trips the `isError` body check automatically.
- **N-04 — fixed by re-measurement.** 120 s run on this machine, driver 616.56:
  **29.0 GiB × 359 full rounds = 86.7 GiB/s, 0 errors** — landing within ~3% of this review's
  84.1 GiB/s two-point extrapolation. The README now states 87 GiB/s with the run length and
  driver, and notes that throughput varies by driver (the original 100+ figure was recorded live
  on 610.88 and does not reproduce on 616.56).

Residuals on D-03 (multi-NVIDIA-GPU adapter identity) and D-04 (per-GPU applied-state files)
remain open and tracked; both require a second NVIDIA card to exercise honestly.

## High

### D-01 — `ApplyOffset` reports `(verified)` when verification did not happen

`src/Afterglow.Core/Tuning/GpuTuner.cs:311-324`

The readback is a single `&&` chain. If `TryGetClockOffset` returns anything other than
`Success`, the chain short-circuits to `false`, the failure branch is skipped, and execution
falls through to:

```csharp
Report(results, knob, rc, detail + " (verified)");
```

The user is told the write was confirmed when nothing was read back.

This is an oversight rather than a design choice: `ApplyPowerLimit` (`:357`) and
`ApplyVoltageBoost` (`:406`) both append `" (verified)"` *inside* the successful-readback
branch. `ApplyOffset` is the only one of the three that appends it unconditionally.

**Why it matters more than the others:** readback verification is the project's headline
honesty claim (README: *"offsets, power limit, and voltage boost are verified by reading the
applied value back"*), and this is the knob users touch most.

**Fix** — move the concatenation inside the branch, matching the other two:

```csharp
var rc = _nvml.TrySetClockOffset(type, clamped);
if (rc == NvmlReturn.Success && _nvml.TryGetClockOffset(type, out var readback) == NvmlReturn.Success)
{
    if (readback.ClockOffsetMHz != clamped)
    {
        results.Add(KnobResult.Fail(knob, $"driver accepted the call but readback shows {readback.ClockOffsetMHz} MHz"));
        return;
    }

    detail += " (verified)";
}

Report(results, knob, rc, detail);
```

### D-02 — A throttle reason this driver reports live is silently dropped

`src/Afterglow.Core/Interop/Nvml/NvmlConstants.cs:100-112`,
`src/Afterglow.Core/Telemetry/ThrottleDescriber.cs:23`

`NvmlClocksEventReasons` stops at `DisplayClockSetting = 0x100`. This machine's GPU reports
bitmask **1024 (`0x400`)** during ordinary operation.

Confirmed by direct invocation:

```text
mask 0x400 -> 0 chip(s): <NOTHING SHOWN TO USER>
mask 0x4   -> 1 chip(s): Power limit
mask 0x404 -> 1 chip(s): Power limit          <- 0x400 contributes nothing
mask 0x200 -> 0 chip(s): <NOTHING SHOWN TO USER>
mask 0x0   -> 0 chip(s): <NOTHING SHOWN TO USER>
```

`Describe()` has no fallback for unrecognized bits, so an unknown reason is indistinguishable
from no throttling at all. The dashboard and the overlay both render an empty chip list.

`docs/verification-rtx5090.md` was captured on driver 610.88, where this line read
`Throttle reasons: None`. The claim has already drifted on 616.56 — the concrete cost of
pinning verification evidence to a single driver build.

**Fix** — two parts:

1. Emit a fallback chip for any set bit that no branch consumed, e.g. *"Other driver-reported
   reason (0x400) — not yet decoded by Afterglow."* This preserves the honesty property under
   future driver changes without needing to know the meaning.
2. Decode `0x200` / `0x400` against a current NVML header and add named entries.

### D-03 — Burn and VRAM tests bind to the default D3D adapter, not the GPU being tuned

`src/Afterglow.Core/Stress/GpuStressTest.cs:228`, `src/Afterglow.Core/Stress/VramTest.cs:193`

```csharp
D3D11.D3D11CreateDevice(null, DriverType.Hardware, ...)
```

The `null` adapter takes whatever DXGI orders first. `adapter.Description` is then read only to
*size* the working set — it is never checked against the NVML/NVAPI device the rest of the app
is tuning and reporting on.

Probed on this machine:

```text
adapter[0] = NVIDIA GeForce RTX 5090       vram=31.4 GiB  vendor=0x10DE
adapter[1] = AMD Radeon(TM) Graphics       vram= 2.0 GiB  vendor=0x1002
adapter[2] = Microsoft Basic Render Driver vram= 0.0 GiB  vendor=0x1414

D3D11CreateDevice(null, Hardware) ==> SELECTED: NVIDIA GeForce RTX 5090 (0x10DE)
```

So it is **correct here** — but by ordering luck, not by construction. On a laptop where the
iGPU drives the display, or any system where the NVIDIA card is not adapter 0, the stress test
would load a different GPU while the UI displays the NVIDIA card's clocks, power and
temperature, and the stability stepper would certify offsets against a GPU that never ran the
workload. That failure is silent and produces a confidently wrong "stable" verdict.

**Latent on this hardware; unsound in general.**

**Fix** — enumerate adapters via `IDXGIFactory1`, match on LUID or on the PCI
bus/device/function already available from `NvmlDevice.TryGetPciInfo`, and pass the explicit
`IDXGIAdapter` into `D3D11CreateDevice`. If no match is found, fail loudly rather than falling
back to `null`.

### D-04 — Multi-GPU is unsupported, and the applied-state file makes it actively wrong

`src/Afterglow.App/ViewModels/*.cs` (all), `src/Afterglow.Core/Tuning/GpuTuner.cs:103`

Two problems that compound.

**1. Every GUI surface is hardwired to `Gpus[0]`** — Dashboard, Tuning, Fans, Metrics,
Stability, Profiles, V/F Curve, the overlay, and the tray tooltip. Only the CLI's `caps` /
`get` / `set` / `reset` honour `--gpu N`.

**2. `AppliedStateStore` is a single global file with a single static lock.** Each `GpuTuner`
constructor does:

```csharp
_appliedLockMHz = AppliedStateStore.Load()?.LockedCoreClockMHz;
```

On a two-GPU system every tuner loads the *same* record. A clock lock applied to GPU 1 via
`--gpu 1` is loaded into GPU 0's tuner at next start, so `ReadCurrent()` reports a lock that was
never applied to that card, and `ApplyLockedClock`'s "release any active lock" path issues an
unlock against the wrong GPU. `RecordFans` has the same collision.

The README's *Honest limitations* section does not mention single-GPU-only — which, given that
the section exists precisely to enumerate what the tool cannot do, is the gap worth closing
first.

**Fix** — key the applied-state file by GPU UUID (already read in `selftest`) and state the
single-GPU-UI limitation in the README. Full multi-GPU UI support is a much larger change and
may not be worth it.

## Medium

### D-05 — The V/F probe restores a range lock as a hard pin

`src/Afterglow.Core/Tuning/VfCurveProbe.cs:150`

The two lock paths have deliberately different semantics:

| Caller | Call | Meaning |
|---|---|---|
| `GpuTuner.ApplyLockedClock` (`:417`) | `TrySetGpuLockedClocks(210, lockMHz)` | range lock — idle downclock still allowed |
| `GpuTuner.LockClockForProbe` (`:448`) | `TrySetGpuLockedClocks(clockMHz, clockMHz)` | exact pin — required for probing |

The probe captures `previousLock = _tuner.AppliedLockMHz` (a bare `uint?`, so the semantics are
lost) and restores it in `finally` through the **probe** helper:

```csharp
if (previousLock is uint restore)
{
    _ = _tuner.LockClockForProbe(restore);   // (restore, restore) — not (210, restore)
}
```

Run a probe while a profile lock is active and the GPU is afterwards pinned at that clock even
at idle — measurably higher idle power and heat. `_appliedLockMHz` stores the same number
either way, so nothing in the UI indicates the change.

**Fix** — track the lock as a `(min, max)` pair rather than a single value, or add
`GpuTuner.RestoreTuningLock(uint)` that re-applies the `210..X` form, and call that from the
probe's `finally`.

### D-06 — `PlanUndervolt` emits unvalidated values as confident advice

`src/Afterglow.Core/Tuning/VfCurveRecorder.cs:149`

The arithmetic itself is correct — verified against a synthetic curve
(900 mV → 2800 MHz, 950 → 2900, 1000 → 3000):

```text
ClockAt(925)                                 = 2850          (linear interp, correct)
PlanUndervolt(900 mV, 2900 MHz, offset 0)    -> offset +100  (= 0 + (2900 - 2800))
PlanUndervolt(900 mV, 2900 MHz, offset +150) -> offset +250
ClockAt(1200)                                = null          (correctly refuses to extrapolate)
```

But the result is bounded by nothing:

```text
PlanUndervolt(900 mV, 9000 MHz, offset 0) -> offset +6200 MHz, lock 9000 MHz
```

`Describe()` renders that in exactly the same authoritative tone as a good plan (*"Hold 9000 MHz
at ~900 mV: core offset +6200 MHz with the clock locked at 9000 MHz"*). The offset is later
clamped to the driver range in `ApplyOffset`; the **lock is never clamped** and goes straight to
`TrySetGpuLockedClocks`, where NVML rejects it. It fails safe — but the user was shown nonsense
first.

Reachability is limited in the GUI because the chart constrains picks to the plotted range.
`PlanUndervolt` is public, and the CLI/MCP paths have no such constraint.

**Fix** — clamp inside `PlanUndervolt` against `TuningCapabilities` (core offset range and
`MaxCoreClockMHz`), and return `null` — or a plan explicitly flagged out-of-range — rather than
a plan that cannot be applied.

### D-07 — `VfCurveRecorder.Load()` skips the validation `Add()` enforces

`src/Afterglow.Core/Tuning/VfCurveRecorder.cs:193`

`Add()` filters every sample: load ≥ `MinLoadPct`, 600 mV ≤ mv ≤ 1300, mhz ≥ 200. `Load()`
restores persisted bins verbatim with no bounds check at all. A corrupted or hand-edited
`vf-curve.json` therefore feeds arbitrary `MaxClock` values into `PlanUndervolt`, which computes
an offset from them and offers it as a hardware write.

**Fix** — apply the same bounds on load, drop bins that fail, and log how many were dropped.

### D-08 — Two samples in a voltage bin are enough to drive a hardware write

`src/Afterglow.Core/Tuning/VfCurveRecorder.cs:84`

```csharp
.Where(kv => kv.Value.Samples >= 2)
```

`Bin.MaxClock` keeps the highest clock ever seen at that voltage and never decays. Because
voltage and clock are read by separate driver calls within one snapshot, a sample taken during a
clock/voltage transition can pair a low voltage with a high clock. One such pairing permanently
poisons that bin — only `Clear()` removes it.

The bias direction is fortunate: an over-estimated `measuredClock` makes `requiredOffset` too
*small*, so the resulting undervolt is less aggressive than promised rather than unstable. That
is the safe direction — but it is nowhere stated as a deliberate choice, and the promise
"hold F at V" is then not met.

**Fix** — require a much higher sample count before a bin is eligible for `PlanUndervolt`
(e.g. ≥ 20), separately from the threshold for *drawing* the curve; surface the per-bin sample
count in the plan text so a thin bin is visible. Consider a high percentile rather than a raw
max.

### D-09 — Tray alerts cross threads without dispatching

`src/Afterglow.App/ViewModels/MainViewModel.cs:122`

```csharp
services.Telemetry.SnapshotTaken += CheckAlerts;
```

`CheckAlerts` runs on the telemetry polling thread and calls `TrayAlert` synchronously, which
`App.xaml.cs:152` forwards to `TrayService.Alert` → `WinForms.NotifyIcon.ShowBalloonTip`. That is
a Win32 UI object created on the UI thread, and `NotifyIcon` is not thread-safe.
`TrayService._lastAlert` is likewise read and written from a background thread without
synchronization.

This is the **only** unmarshaled cross-thread UI path in the app — the other 14 sites all use
`Dispatcher.BeginInvoke`, and there are zero blocking `Dispatcher.Invoke` calls anywhere (which
is why the app has no deadlock class).

The one-alert-per-minute rate limit is *not* a defect; it lives correctly in `TrayService`.

**Fix** — wrap the `TrayAlert` invocation in `Application.Current?.Dispatcher.BeginInvoke`, as
every sibling handler in the same constructor already does.

### D-10 — Manual fan control is recorded even when the fan command failed

`src/Afterglow.Core/Fans/FanControlService.cs:76-83`

```csharp
uint duty = TuningMath.NormalizeFixedFanDuty(dutyPct, _tuner.Capabilities.FanMinDutyPct);
Command(duty);                                   // may fail (e.g. not elevated)
AppliedStateStore.RecordFans("fixed", duty);     // recorded unconditionally
```

`Command()` sets `_weControlFans = true` only on success, so the in-memory state is right — but
the persisted state claims Afterglow took manual fan control regardless. On the next launch,
crash recovery reads that record and reports manual fan control that was never established.

**Fix** — record only when `Command()` succeeded, i.e. gate on `_weControlFans`.

### D-11 — MCP `isError` stays `false` when every tuning knob fails

`src/Afterglow.Cli/McpCommand.cs:134-155`

`isError` is set only when the tool delegate *throws*. A tuning apply where every knob failed
returns `isError: false`. Confirmed live (unelevated):

```json
{"content":[{"type":"text","text":"{\"all_succeeded\":false,\"results\":[
  {\"knob\":\"memory offset\",\"applied\":false,\"detail\":\"needs administrator rights\"},
  {\"knob\":\"core offset\",\"applied\":false,\"detail\":\"needs administrator rights\"}],...}"}],
 "isError":false}
```

The payload is truthful, so an agent that parses the body is fine. An agent that checks the
MCP-standard `isError` flag — the normal thing to do — concludes the tuning was applied. For a
surface whose stated contract is *"every result is reported truthfully"*, and which is meant to
drive autonomous tuning loops, the flag should agree with the body.

**Fix** — set `isError = true` when the tool result carries `all_succeeded: false`.

### D-12 — `Start()` after `Stop()` spawns a second worker and un-stops the first

`src/Afterglow.Core/Stress/GpuStressTest.cs:177-190`, `src/Afterglow.Core/Stress/VramTest.cs:112-160`

```csharp
public bool IsRunning => _thread is { IsAlive: true } && !_stop;

public void Start()
{
    if (IsRunning) return;
    _stop = false;
    _thread = new Thread(Run) { ... };
    _thread.Start();
}
```

Once `Stop()` sets `_stop = true`, `IsRunning` is `false` while the worker is still alive. A
`Start()` in that window passes the guard, sets `_stop = false` — which resurrects the *old*
thread's `while (!_stop && healthy)` loop — and starts a second one. Two D3D devices, two
progress streams, and the first thread is no longer reachable to stop.

**Latent:** every call site (`StabilityViewModel:187`, `StressCommand:39`, `McpCommand:451`,
`ProfileCertifier:180`, `StabilityStepper:271`, `VfCurveProbe:98`) constructs a fresh instance
rather than reusing one, and the stepper/certifier use the joining `StopAndWait`.

**Fix** — guard on `_thread is { IsAlive: true }` alone, or make the class single-use and throw
on restart.

### D-13 — `CommandFailed` is raised while holding `_lock`, and has no subscribers

`src/Afterglow.Core/Fans/FanControlService.cs:59,144`

`Command()` invokes the event from inside `lock (_lock)`. If a subscriber ever blocks on the UI
thread while the UI thread is calling `SetFixed()` / `SetAuto()` (which take `_lock`), that is a
lock-order deadlock. It cannot fire today because the event has **zero subscribers** anywhere in
the solution — which is itself the finding: a fan command failing (lost elevation, driver
refusal) reaches the log and nothing else, while the project's premise is that failures are
surfaced.

**Fix** — subscribe it to the existing tray-alert path, and raise it outside the lock.

### D-14 — `_lock` is held across driver calls

`src/Afterglow.Core/Fans/FanControlService.cs:101-127`

`OnSnapshot` holds `_lock` for the whole body, including `Command()` → `SetAllFansRaw` →
NVAPI/NVML. A slow driver call blocks the telemetry poller and any UI-thread call into the
service. At a 1 s poll interval this is unlikely to be visible, but holding a lock across a
kernel-mode transition is the pattern that makes it visible later.

**Fix** — compute the desired duty under the lock, release, then command.

### D-15 — NVML fan fallback has no upper clamp

`src/Afterglow.Core/Tuning/GpuTuner.cs:496`

```csharp
_nvml.TrySetFanSpeed(f, Math.Max(dutyPct, dutyPct == 0 ? 0 : Capabilities.FanMinDutyPct));
```

The NVAPI path clamps with `Math.Min(dutyPercent, 100)` (`NvapiApi.TrySetAllFans`); this fallback
does not, so a value above 100 reaches the driver and is rejected there. The expression is also
needlessly convoluted — `dutyPct == 0 ? 0 : min` inside a `Math.Max` with `dutyPct` reduces to a
two-branch conditional.

**Fix** — `dutyPct == 0 ? 0 : Math.Clamp(dutyPct, Capabilities.FanMinDutyPct, 100)`.

### D-16 — Hardcoded 210 MHz clock-lock floor

`src/Afterglow.Core/Tuning/GpuTuner.cs:417`

```csharp
var rc = _nvml.TrySetGpuLockedClocks(210, lockMHz);
```

`210` is commented as a "P8-style floor" but is not derived from anything the driver reported. On
a GPU whose minimum supported locked clock is higher, NVML returns `InvalidArgument` and the
lock — the mechanism the entire RTX 50 undervolt strategy rests on — fails with an opaque
message.

**Fix** — derive the floor from a driver-reported minimum where available, or retry with the
driver's minimum on `InvalidArgument`.

### D-17 — Three NVAPI delegates and their structs are dead code

`src/Afterglow.Core/Interop/Nvapi/NvapiNative.cs:369,387,390`

`GetThermalSettingsDelegate`, `GetCoolerSettingsDelegate` and `SetCoolerLevelsDelegate` have zero
uses outside their own declarations, along with `NvThermalSettings` / `NvThermalSensor`,
`NvCoolerSettings` / `NvCooler`, `NvCoolerLevels` / `NvCoolerLevel` and the corresponding
`NvapiIds` constants — roughly 70 lines of unexercised P/Invoke surface with hand-computed struct
layouts that nothing validates.

This matters more here than ordinary dead code: these are marshaling declarations for a driver
interface, and the project's stated position is that its interop set is verified. `DrsApi` shows
the right instinct (see *Credit where due*); these have no equivalent guard because nothing ever
calls them.

**Fix** — delete them. Reinstate with a size self-check if a caller is ever added.

### D-18 — `NvapiGpu.Architecture` is publicly mutable with hidden init-order coupling

`src/Afterglow.Core/Interop/Nvapi/NvapiApi.cs:83`

```csharp
public uint Architecture { get; set; }
```

`GetPrivateThermals()` maps thermal channels off this value (`>= 10` → memory junction on channel
2; `8` → hot spot 1 / mem 7; otherwise 1 / 9). It defaults to `0`, which silently selects the
pre-Ada mapping. `GpuManager` sets it before constructing the poller, so the app is correct — but
`NvapiApi.GetGpus()` is public, and any other caller that reads thermals before assigning
`Architecture` gets wrong channels with no error.

**Fix** — make it a constructor parameter, or return `(null, null)` from `GetPrivateThermals`
until it has been set explicitly.

### D-19 — GPU pairing keyed on PCI bus only

`src/Afterglow.Core/Hardware/GpuManager.cs:58`

```csharp
nvapiByBus[busId] = gpu;
```

NVML and NVAPI devices are paired on bus number alone, discarding domain, device and function
(all four are available from `TryGetPciInfo`). Two GPUs sharing a bus number in different domains
collide, and the later one silently overwrites the earlier in the dictionary.

Very unlikely on consumer hardware; trivially avoided.

**Fix** — key on the full `domain:bus:device.function` tuple.

### D-20 — `Validate()` uses a ±1500 MHz constant unrelated to the driver range

`src/Afterglow.Core/Profiles/TuningProfile.cs:93`

The driver reports −1000…+1000 for core on this card, but the profile validator rejects only
outside ±1500. Values in the 1000–1500 band pass validation and are then silently clamped at
apply. The rejection message an agent or CLI user sees cites a bound with no relation to their
hardware — confirmed live via MCP:

```text
apply_tuning core_offset_mhz=99999 -> "Core offset outside ±1500 MHz."
```

Behaviour is safe (clamped and reported); the message is misleading.

**Fix** — keep ±1500 as the schema sanity bound, but have the MCP/CLI error path report the
driver-reported range from `TuningCapabilities`.

### D-21 — Narrow catch clauses on a background thread

`src/Afterglow.Core/Stress/GpuStressTest.cs:521,529`

```csharp
catch (SharpGenException ex) { ... }
catch (Exception ex) when (ex is InvalidOperationException or DllNotFoundException) { ... }
```

Anything else thrown on the burn thread — including from Vortice interop or an allocation —
propagates out of a background thread and terminates the process with no report and no
`ResetToDefaults`. That is the worst possible outcome for a tool that may be holding an overclock
at the time.

Low likelihood; high blast radius.

**Fix** — add a final `catch (Exception ex)` that reports `StressState.Failed` with the message,
matching the existing top-level handlers in `App.xaml.cs` and `TelemetryService`.

## README claims the code does not support

The project's entire positioning is honesty, so these are graded against that standard rather than
normal marketing latitude.

**R-01 — "a deterministic compute workload is verified result-for-result — a single flipped bit
reports unstable"**

`GpuStressTest.cs:67-68`. The output is `1 << 20` = 1,048,576 elements × 16 B = 16 MiB. The verify
slice is `CheckElements` = 16,384 × 16 B = 256 KiB, always at offset 0.
**16,384 / 1,048,576 = 1/64 = 1.5625%** — always the same first 64 of 4,096 thread groups.

Sampling is a defensible design (instability is rarely localized, and group→SM assignment varies
across dispatches), but "result-for-result" is not a description of it.

*Fix:* describe it as a periodically verified slice, or verify a rotating window.

**R-02 — "a fully autonomous find-my-best-clocks loop"** (MCP section)

The server exposes 9 tools: `get_capabilities`, `get_telemetry`, `apply_tuning`,
`reset_defaults`, `run_stress`, `run_vram_test`, `list_profiles`, `save_profile`,
`apply_profile`. None is an autotune. `StabilityStepper` — which *is* the auto-stepper — is not
exposed over MCP. What ships is primitives plus a tool description instructing the agent to build
the loop itself.

*Fix:* either expose `StabilityStepper` as a tool, or reword to "the primitives for an autonomous
loop".

**R-03 — "offsets, power limit, and voltage boost are verified by reading the applied value
back"**

True for two of the three. See D-01.

**R-04 — "Plain-language throttle analysis"**

Currently produces nothing for what this driver actually reports. See D-02.

Not a claim, but a matching omission: *Honest limitations* does not mention that the GUI is
single-GPU only (D-04).

## Test-coverage gaps

69 tests pass in ~1 s. The test *names* are genuinely good — they assert real invariants
(zero-RPM latching, certification staleness, crash-signature classification, VRAM chunk planning
refusing to fake a test). Coverage is concentrated on pure helpers.

Untested:

`GpuTuner` and add a fake that can return `NotSupported` from getters. That one refactor makes
four of the findings above regression-testable.

## Credit where due

Not defects — recorded because they should survive any refactor.

- **`DrsApi.TryCreate` (`:170-176`)** refuses to initialize unless
  `sizeof(NvdrsProfile) == 4116 && sizeof(NvdrsApplication) == 20492 && sizeof(NvdrsSetting) == 12320`.
  This is the single most dangerous write path in the product — persistent, driver-wide, and
  active when Afterglow is not running — and it is the best-defended. A marshaling regression
  fails loudly instead of corrupting the driver's settings store. D-17 is the same idea applied
  inconsistently elsewhere.
- **Frame-metric math is exactly right**, hand-verified rather than taken from the tests. For 99
  frames @ 10 ms + 1 @ 100 ms: harmonic average `100 × 1000 / 1090 = 91.7431` ✓; R-7 p99 rank
  `0.99 × 99 = 98.01` → `10 + 0.01 × (100 − 10) = 10.9 ms` → `91.7431 fps` ✓; worst-1% average
  = `10 fps` ✓. Keeping P1 (interpolated percentile) distinct from 1% low (mean of the worst 1%)
  is more rigorous than most commercial tools.
- **The burn test does what it says.** 25 s run, 7,305 dispatches, 0 errors, independently
  corroborated by `nvidia-smi`: 100% GPU util, ~60% memory-controller util, 2,985–3,000 MHz,

- **Demo mode cannot touch hardware** — `AppServices.Create` sets `Gpus = []` and an empty
  `FanControl` dictionary, and every page carries a `DEMO DATA` badge.
- **Unelevated degradation is real** — `MONITORING ONLY` badge, every control gated on `CanTune`,
  live values still displayed.
- **Threading discipline** — 14 cross-thread marshaling sites, all `BeginInvoke`, zero blocking
  `Dispatcher.Invoke` anywhere. D-09 is the lone exception.
- **Hygiene** — 0 TODO/FIXME/HACK, 0 empty catch blocks, 0 `async void`, 70 catches all
  exception-filtered except 3 correctly-placed top-level handlers, 0 warnings under
  `TreatWarningsAsErrors` + `latest-recommended`, `artifacts/` gitignored, 4.9 MB repo, PresentMon

## Resolution (same day)

All 22 defects and all 4 README claims were addressed in the follow-up commit; live-verified
on the same hardware where the review ran (burn + VRAM test clean on the explicitly-selected
adapter, MCP `isError:true` confirmed on a failed unelevated apply). Notes where the fix
differs from the suggestion:

- **D-01, D-09, D-10, D-11, D-12, D-13, D-14, D-15, D-21** — fixed as suggested.
- **D-02** — unknown-bit fallback chip added (regression-tested); 0x200/0x400 remain
  *undecoded by name* deliberately: no current public NVML header naming them was available,
  and inventing names would trade one honesty bug for another.
- **D-03** — fixed via explicit adapter selection (NVIDIA vendor, largest dedicated VRAM,
  loud failure when absent) rather than LUID matching; covers the iGPU-first case the finding
  is about. Exact-LUID pairing can ride along with full multi-GPU work.
- **D-04** — applied-state records now carry the GPU UUID and a tuner only adopts a persisted
  lock stamped with its own UUID (or a legacy unstamped record); README's Honest limitations
  now states the single-GPU GUI. Fan/pending records remain global, matching the single-GPU UI.
- **D-05** — `GpuTuner.RestoreTuningLock` added (range form); the probe restores through it.
- **D-06/D-07/D-08** — plans validate against driver capabilities when available plus schema
  bounds always; `Load()` enforces `Add()`'s bounds and logs drops; plan eligibility needs
  ≥ 20 samples per bin (drawing still needs 2) and the plan text now shows the bin's sample
  count. All covered by new unit tests.
- **D-16** — floor kept at 210 (NVML exposes no queryable minimum) but named as a constant and
  the InvalidArgument failure now says exactly what was rejected and asks for a report.
- **D-17** — dead delegates, structs, and IDs deleted.
- **D-18** — `GetPrivateThermals` returns nothing until `Architecture` is set, instead of
  guessing the pre-Ada channel map.
- **D-19** — NVAPI exposes only the bus number (no domain/device via the bound interface), so
  exact-tuple keying isn't possible; instead a bus-number collision now un-pairs both GPUs
  loudly rather than silently overwriting.
- **D-20** — MCP validation errors now include this GPU's driver-reported ranges.
- **D-22** — field renamed to `ReservedAfterCoreMicrovolts` and documented; deleting it would
  change the marshaled layout.
- **R-01** — fixed in code, not prose: verification now walks a rotating 256 KiB window that
  covers the entire 16 MiB output each 64-check cycle; README describes exactly that.
- **R-02** — fixed by shipping the claim: `find_stable_offset` exposes the stepper as a single
  autonomous MCP tool.
- **Test seam (`IGpuWriteTarget`)** — deliberately deferred: it is the right refactor and the
  highest-value one, but it reshapes the most safety-critical file and deserves its own
  focused change, not a slot at the end of a 22-fix pass. The newly testable surfaces
  (ThrottleDescriber, VfCurveRecorder) got their tests now.
