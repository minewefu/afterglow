# Driver API research — Intel IGCL + Level Zero Sysman

This document records every Intel driver interface Afterglow's Arc support uses, where
each fact came from, and what was verified on real hardware: an **Intel Arc B390 iGPU
("Arc G3 Extreme") in a OneXPlayer 3 handheld, driver 32.0.101.8991, IGCL runtime 1.1,
Windows 11 Home 26200**. Nothing in the interop layer is based on guesswork: every
struct layout is compiled from Intel's official headers and pinned by unit tests, and
`afterglow-cli selftest` probes each capability live before the UI exposes it. Where
this device does not answer, the finding is recorded as *this device's* answer, never
generalized to other Arc hardware — discrete B-series cards are expected to answer
differently (field reports wanted).

## IGCL — Intel Graphics Control Library (`ControlLib.dll`)

Primary sources: the official C header `igcl_api.h` v1-r1 from
github.com/intel/drivers.gpu.control-library (Intel's public, supported control API —
the same one Arc Control was built on), plus Intel's sample apps in the same repo for
calling conventions the header leaves open (notably the `pDeviceID` idiom). The
runtime ships with the Intel graphics driver as `ControlLib.dll` in System32; the
header itself never names the DLL — the name comes from the IGCL distribution layout.

Key facts:

- **Calling convention** is `__cdecl` with undecorated C exports; handles are opaque
  pointers. `ctlInit` takes `ctl_init_args_t` with
  `CTL_INIT_FLAG_USE_LEVEL_ZERO` — without that flag the telemetry/frequency/component
  APIs do not answer. `ctlClose` may return `0x00000001`
  (STILL_OPEN_BY_ANOTHER_CALLER), which is a success code.
- **Every API struct starts `uint32_t Size; uint8_t Version;`** and the caller must
  set both before the call. `Size` mismatches fail with `INVALID_SIZE`/`UNSUPPORTED_SIZE`
  — which makes the driver a live check on each struct's *total size*: a call
  succeeding with `Size = Marshal.SizeOf<T>()` confirms the overall size matches the
  driver's build of the struct. Interior field offsets are not checked by the driver;
  those are pinned by the `IgclStructLayoutTests` offset assertions. `Version` gates
  newer fields (adapter properties need Version 2 for the
  PCI BDF; power telemetry and overclock properties need Version 1 for their newer
  tail fields). Afterglow requests the newer version first and retries with 0 on
  `UNSUPPORTED_VERSION`. Two structs grew physically at V1 (`ctl_power_telemetry_t`
  808 → 1024 bytes, `ctl_oc_properties_t` 296 → 440 — no reserved tail to absorb the
  new fields), so a size rejection triggers a last-resort retry with the historical
  pre-V1 size for runtimes built against the older header; both historical sizes are
  pinned in the layout tests.
- **No `#pragma pack` anywhere** — natural MSVC alignment. C++ `bool` fields are
  **1 byte** (marshaled as `byte`; the default C# `bool` marshaling of 4 bytes would
  shift every following field). `ctl_data_value_t` is an 8-byte union
  (`LayoutKind.Explicit`).
- **Layout ground truth**: expected sizes for the `IgclStructLayoutTests` /
  `ZesStructLayoutTests` unit tests were generated by compiling the official headers
  with `clang -fsyntax-only -Xclang -fdump-record-layouts-complete` targeting
  `x86_64-pc-windows-msvc` (clang 22.1.8), on the dev machine, and cross-checked
  against Intel's sample sources. Key pinned sizes (x64): `ctl_init_args_t` 36,
  `ctl_device_adapter_properties_t` 320, `ctl_oc_telemetry_item_t` 24,
  `ctl_power_telemetry_t` 1024, `ctl_oc_properties_t` 440, `ctl_power_limits_t` 36,
  `ctl_fan_config_t` 936. The tests also pin the interior offsets of the two inline
  arrays in the telemetry block (`psu` at 408, `fanSpeed` at 688) where a packing
  mistake would first corrupt data.
- **`pDeviceID` is a caller-allocated buffer**: the header says only "OS specific
  Device ID". Intel's own samples allocate `sizeof(LUID)` = 8 bytes with
  `Version = 2`, and the driver writes the **Windows adapter LUID** — the same LUID
  DXGI reports, which is how Arc stress-test adapter binding can be made exact. LUIDs
  are not stable across reboots and are never used as persistent identity.
- **Telemetry** (`ctlPowerTelemetryGet`): one bulk struct of `ctl_oc_telemetry_item_t`
  entries, each self-describing (`bSupported`, units, data type). Energy counters are
  monotonic (`watts = ΔE/Δt`), activity counters are monotonic busy-seconds
  (`util% = 100·Δbusy/Δt`). The driver refreshes at most every **50 ms**; polling
  faster returns identical data. The V1 `timeStamp` is documented as seconds since
  the Unix epoch but on this driver counts from boot — Afterglow only ever uses it
  as a delta, which both semantics support.
- **Overclock** (`ctlOverclockGetProperties` + per-knob get/set): capability is
  reported per knob via `ctl_oc_control_info_t` (`bSupported`, min/max/step/default,
  units). **The V1/V2 getters can "succeed" and return zeros even when the
  capability report says unsupported** — verified on this device — so support gating
  keys off `bSupported`, never off getter status. Writes require
  `ctlOverclockWaiverSet` first (the driver refuses otherwise); Afterglow calls it
  only after the user accepts an in-app warning. V2 entry points
  (`...SetV2`) are unit-agnostic — the authoritative unit is the knob's `units`
  field; V1 entry points use fixed units (MHz / mV / **milliwatts** / °C).
- **Power domains** (`ctlEnumPowerDomains` → `ctlPowerGetLimits`/`SetLimits`):
  Sysman-style PL1 (sustained + tau) / PL2 (burst) / PL4 (peak AC/DC) limits in
  milliwatts. Documented gotcha: `ctlPowerSetLimits` fails with `NOT_AVAILABLE`
  while an OC power limit is active — the two power paths are mutually exclusive.
- **Frequency clamps** (`ctlFrequencySetRange`): per-domain (GPU / MEMORY / MEDIA)
  min/max in MHz; 0 = hardware limit, −1 = restore factory value.
- **Fan control** (`ctlEnumFans` → fixed speed / 32-point temp table / default
  mode) exists in the API; devices whose fans are EC-controlled enumerate zero fans.

### What this device answers (selftest, 2026-09-01, driver 32.0.101.8991)

Verified working: device enumeration and identity (name, 0x8086:0xB082, BDF 00:02.0,
LUID, integrated flag, driver version), bulk telemetry at Version 1 (GPU clock, GPU
energy counter → watts, global/render/media activity counters → utilization, throttle
flag bits), frequency domains GPU (100–2300 MHz) and MEDIA (100–1200 MHz) both
`canControl=true` with readable state (actual/request/tdp/efficient) and readable
range clamp, one SHARED (system) memory module with allocatable-budget state
(24 GiB physical, ~13.4 GiB GPU budget), engine groups GT/RENDER/MEDIA with working
activity counters, PCI properties (ReBAR flag; link gen/width honestly −1 on an iGPU).

Honestly absent on this device — every one re-probed live at startup, never assumed:

| Capability | This device's answer |
|---|---|
| Temperature sensors | zero sensors enumerated (both IGCL and Sysman); bulk-telemetry temperature item `bSupported=false` |
| Fans | zero fans enumerated — EC/firmware-controlled on this handheld |
| IGCL power domains | zero domains enumerated (no PL1/PL2/PL4 read or write path via IGCL) |
| Overclock block | `bSupported=false`, all seven knobs unsupported (no frequency offset, no voltage offset, no OC power limit, no temperature limit, no VRAM speed limit, no V/F-curve limits) |
| V/F curve read | entry points exist but return `ErrorDataRead` |
| VRAM telemetry items | all `bSupported=false` (shared LPDDR — no separate VRAM rail/sensors) |
| Memory bandwidth counters | `UNSUPPORTED_FEATURE` from both stacks |

## Level Zero Sysman (`ze_loader.dll`)

Primary sources: the official C header `zes_api.h` from
github.com/oneapi-src/level-zero. Loaded through `ze_loader.dll` (ships with the
Intel driver); initialized via `zesInit` — the modern path that needs no
`ZES_ENABLE_SYSMAN` environment variable.

Key facts:

- Structs use the `stype`/`pNext` convention: the caller sets `stype` to the struct's
  `zes_structure_type_t` value and zeroes `pNext`. `ze_bool_t` is 1 byte. Layouts
  pinned by the same clang procedure as IGCL (e.g. `zes_freq_state_t` 64,
  `zes_power_properties_t` 40, `zes_mem_properties_t` 48).
- **Sysman is telemetry-only in Afterglow, by project policy**: the header marks its
  entire overclock block "[DEPRECATED] No longer supported" (no successor named) and
  deprecates the legacy `zesPowerGet/SetLimits` in favor of
  `zesPowerGet/SetLimitsExt` — which are still Sysman APIs. Afterglow routes all
  hardware writes through IGCL and uses Sysman as the second opinion on reads.
- `zesPowerGetEnergyCounter` returns a monotonic **microjoule** counter with a
  microsecond timestamp — exact average power over any window, cross-checking
  IGCL's joule counters.
- `zes_freq_state_t` carries the request/TDP-max/efficient/actual frequency tuple
  plus a throttle-reason bitmask (PL1/PL2/PL4/thermal/PSU/software/hardware) —
  distinguishing "driver asked for less" from "hardware capped it".

### What this device answers

One Sysman device (BDF 0000:00:02.0, matching IGCL). One power domain:
`canControl=false`, **default limit 25.0 W** (the handheld's package TDP), min/max
unknown, energy counter working (recorded run: 0.3 W over the selftest's ~100 ms
idle window, vs 0.2 W from IGCL's GPU energy counter over its ~150 ms window in the
same run — both idle-level readings that vary run to run; numeric agreement between
the two counters over short idle windows is not yet established). Frequency domains
mirror IGCL (GPU + MEDIA, `canControl=true`). Engine
groups ALL/COMPUTE_ALL/MEDIA_ALL with working activity. Zero temperature sensors,
zero fans, memory module SHARED with the same budget numbers as IGCL, bandwidth
counters unsupported.

## Consequences for the port (recorded, not assumed)

- **TDP writes have no answering path on this device yet**: IGCL enumerates no power
  domains, the IGCL OC power limit is unsupported, and Sysman's power domain says
  `canControl=false`. Frequency-range clamping *is* controllable and is the
  driver-supported lever this device offers. Whether `ctlFrequencySetRange` /
  OC writes actually stick (and verify by readback) is a milestone-3 question;
  nothing here has attempted a write yet — selftest is read-only.
- **GPU temperature is not exposed** by either stack on this device. The dashboard
  will say so rather than substitute a number from an undocumented source.
- The shared-memory module (location SYSTEM) is the honest signal the VRAM test
  uses to refuse or re-plan instead of pretending dedicated VRAM exists.
